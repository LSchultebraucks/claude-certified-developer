Die 4 Lösungsmuster der Prüfung

  1. Deterministisch schlägt probabilistisch, wenn eine Garantie verlangt ist („muss immer", „nie", Compliance, Geld, Identität) → Hook, Gate, Permission, Schema – nicht ein stärkerer Prompt.
  2. Ursache auf der richtigen Ebene beheben: falsches Tool → Tool-Beschreibung; erfundene Werte → nullable Feld; Subagent fehlt Info → explizit übergeben.
  3. Verhältnismäßig: Die einfachste Lösung, die das Problem vollständig löst, schlägt Klassifikator, Fine-Tuning, zusätzliche Agent-Ebene, größeres Modell/Kontextfenster.
  4. Qualifier lesen: „most effective first step", „most reliable", „lowest cost while meeting SLA" – mehrere Optionen sind möglich, nur eine ist am besten.

D1 Agentic Architecture & Orchestration 27 %

1.1 Agentic Loop – die erwartete Form

messages = [{"role": "user", "content": task}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":   # end_turn → fertig
        break
    results = [run_tool(b) for b in resp.content
               if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})
    # tool_result-Blöcke mit passender tool_use_id
stop_reasonBedeutung → Aktion
tool_useTools gewünscht → alle ausführen, Ergebnisse anhängen, erneut aufrufen
end_turnFertig → Loop verlassen, Antwort zurückgeben
max_tokensBudget mitten in Antwort erschöpft → erhöhen / fortsetzen, nicht als fertig werten
pause_turnServer-Tool-Loop pausiert → Antwort zurückschicken, Claude macht weiter
refusalAbgelehnt → behandeln/anzeigen, nicht blind wiederholen

1.1 Anti-Patterns im Agent LoopPrüfen, ob die Antwort „fertig klingt" · stoppen, sobald ein Textblock kommt · Iterations-Cap als primäres Stoppsignal (Cap = Sicherheitsnetz, das flaggt/wirft, kein stilles „done") · Tool-Results (auch Fehler) nicht in die History schreiben · nur einen von mehreren tool_use-Blöcken beantworten.

1.2 Multi-Agent-Orchestrierung (Hub-and-Spoke)

  • Coordinator zerlegt, delegiert, leitet alle Kommunikation, aggregiert, entscheidet über weitere Iterationen. Subagents reden nie direkt miteinander (Beobachtbarkeit, Konfliktlösung).
  • Isolation: Jeder Subagent hat eigenen Kontext; sieht nur Delegations-Prompt + eigenen System-Prompt, Tools (ggf. CLAUDE.md).
  • Coverage-Lücke trotz guter Subagent-Arbeit → Fehler liegt in der Zerlegung des Coordinators (zu eng), nicht bei den Subagents.
  • Aufwand skaliert mit der Frage: einfache Faktenfrage ≠ volle Pipeline.

1.3 Subagent-Aufruf & Kontextübergabe

  • Coordinator braucht das Task/Agent-Tool in allowed_tools – sonst kann er nicht delegieren („delegiert nie").
  • AgentDefinition(description, prompt, tools): description steuert, wann delegiert wird.
  • Explizit übergeben: bisherige Findings, Constraints, Quellen-Metadaten, erwartetes Output-Format.
  • Rückgabe als strukturierte Daten mit Metadaten (URL, Datum, Confidence).
  • Parallel: mehrere Task-Aufrufe in einer Antwort emittieren.
options = ClaudeAgentOptions(
  allowed_tools=["Task", "Read", "Grep", "Glob"],
  agents={"web-researcher": AgentDefinition(
    description="Searches the web for one sub-question.",
    prompt="Return JSON: [{claim, source_url, published,
            excerpt}]. Never drop dates.",
    tools=["WebSearch", "WebFetch"])})
Falle„Größeres Kontextfenster / größeres Modell für den Subagent" – irrelevant, die Info wurde nie übergeben. Subagents teilen keine Konversation mit dem Coordinator (höchstens das Dateisystem).

1.4 Workflow-Enforcement & Handoff

  • Prerequisite Gate im Code: process_refund blockiert, bis get_customer eine verifizierte ID geliefert hat. Gate gibt strukturierten Fehler zurück (was fehlt) – kein stilles Blocken.
  • Mehrteilige Anfragen (Retoure + Adressänderung + Rechnungsfrage) in Teilanliegen zerlegen, jedes abarbeiten.
  • Handoff an Menschen: knappe strukturierte Zusammenfassung (Kunden-ID, Bestell-IDs, Beträge, Bisheriges, Ursache, empfohlene Aktion) – kein Transkript-Dump.
Falle„System-Prompt verschärfen / Few-Shot / GROSSBUCHSTABEN" bei Compliance-Fehlern → bleibt probabilistisch (Fehlerrate > 0). Gate oder Hook wählen.

D2 Tool Design & MCP Integration 18 %

2.1 Tool-Interfaces

  • Die Beschreibung ist das primäre Auswahlsignal: Zweck, Input-Formate, Beispiel-Queries, Edge Cases, wann dieses statt des ähnlichen Tools.
  • Generische Tools splitten: analyze_document → extract_data_points, summarize_content, verify_claim_against_source. Überlappende umbenennen.
FalleAls erster Fix „Routing-Klassifikator bauen" (overengineered), „Tools zusammenlegen" (versteckt Mehrdeutigkeit in Parametern) oder Few-Shot als Hauptfix (Tokens pro Call, skaliert nicht). Erst Beschreibungen.

2.2 Strukturierte Fehler für MCP-Tools

{ "isError": true,

   "{\"errorCategory\":\"transient\",\"isRetryable\":true,

Nie [] bei einem Fehler zurückgeben (stiller Fehler als Erfolg getarnt = fast immer die schlechteste Option). Generisches „Operation failed" verhindert passende Recovery. 2.3 Tool-Verteilung & tool_choice

  • Zu viele Tools verschlechtern die Auswahl: 4–5 fokussierte pro Agent schlagen 18. Tools nach Rolle scopen; für häufigen Cross-Role-Bedarf ein schmales Zusatz-Tool.
{"type":"auto"}darf auch nur Text antworten
{"type":"any"}muss irgendein Tool aufrufen → strukturiert, wenn Dokumenttyp unbekannt (Claude wählt Schema)
{"type":"tool","name":"x"}muss x aufrufen → bekannter, fester Schritt
{"type":"none"}kein Tool
Falleauto, obwohl „immer strukturierte Daten" verlangt ist. Forced Tool, obwohl das richtige Tool vom Input abhängt (→ any).

3.2 Slash Commands & Skills

--- .claude/skills/review-api/SKILL.md
name: review-api
description: Review an API route against our REST
  conventions. Use when asked to review endpoints.
argument-hint: "[path to route file]"
allowed-tools: Read, Grep, Glob
context: fork
---
Review $ARGUMENTS against docs/api-conventions.md.
Report only violations, with line numbers.
  • context: fork → läuft in isoliertem Subagent-Kontext; verbose Skills fluten sonst den Hauptkontext.
  • allowed-tools → „nur auditieren, nicht ändern" deterministisch machen.
  • argument-hint / $ARGUMENTS → Parameter.
  • Skill = On-Demand-Workflow · CLAUDE.md = immer aktive Konventionen. Team-Command in .claude/commands/ (Repo), nicht ~/.claude/.

3.3 Path-specific Rules

--- .claude/rules/testing.md
paths:
  - "**/*.test.ts"
  - "**/*.test.tsx"
---
Use Vitest and Testing Library. One behaviour per test.

Wählen, wenn Konventionen über viele Verzeichnisse verteilt gelten (z. B. alle Testdateien). Verzeichnis-CLAUDE.md würde Duplikate erfordern; Root-CLAUDE.md lädt Irrelevantes in jede Session; ein Skill wird nicht automatisch angewendet.

3.4 Plan Mode vs. direkte Ausführung

Plan Modegroß, mehrere Dateien, architektonisch, mehrdeutig, riskant (z. B. Migration, sweeping Refactor) – Alternativen abwägen, bevor Code entsteht
Direktklein, klar, eine Datei (Bugfix mit klarer Ursache, Validierung ergänzen)
Explore-Subagentverbose Discovery isolieren – nur die Zusammenfassung landet im Hauptkontext

Kombinierbar: erst planen, dann ausführen. Plan Mode für jede Kleinigkeit = Overhead.

3.5 Iterative Verfeinerung

  • Konkrete Input/Output-Beispiele statt längerer Prosa bei mehrdeutigen Transformationen.
  • Test-driven: fehlschlagende Tests / Stacktrace einfügen statt beschreiben.
  • Interview-Pattern: in unbekannter Domäne erst Claude Fragen stellen lassen.
  • Zusammenhängende (interagierende) Probleme gebündelt lösen, unabhängige nacheinander.

3.6 CI/CD-Integration

claude -p "Review the diff against CLAUDE.md. Report only
  bugs and security issues." --output-format json \
  --json-schema "$(cat review-schema.json)" > review.json
  • -p / --print = nicht-interaktiv; ohne hängt der Job und wartet auf Eingabe.
  • --output-format json + --json-schema → maschinenlesbar (Inline-PR-Kommentare) – kein Regex auf Freitext.
  • Review-Kriterien & Testkonventionen in CLAUDE.md → CI bekommt denselben Kontext wie Entwickler.
  • Review durch separate Instanz, nicht die generierende Session.
  • Bisherige Findings mitgeben → Re-Runs melden nur neue/ungelöste Punkte (keine Duplikat-Kommentare).
  • Blockierender Pre-Merge-Check → synchron, nie Batch API.

D4 Prompt Engineering & Structured Output 20 %

4.1 Explizite Kriterien & Präzision

  • Konkrete kategoriale Kriterien statt „sei konservativ / nur wichtige Probleme": was melden, was überspringen (z. B. Stil, Naming, TODOs).
  • Severity-Definitionen mit Beispielen.
  • Kategorien mit hoher False-Positive-Rate vorübergehend abschalten, um Vertrauen in die präzisen wiederherzustellen; dann nachschärfen.
Falle„Nur Findings mit Confidence > 0,8" als Hauptfix – selbstberichtete Confidence ist unkalibriert. Erst Kriterien.

4.2 Few-Shot Prompting

  • 2–4 gezielte Beispiele für mehrdeutige Grenzfälle, die das Reasoning zeigen (nicht nur das Label).
  • Formate variieren (Rechnungslayouts) → weniger Halluzination bei neuen Layouts; demonstriert Output-Format.
  • 10 offensichtliche Beispiele lehren die Grenze nicht. Few-Shot ersetzt kein Schema (macht JSON wahrscheinlich, nicht garantiert).

4.3 Structured Output via Tool Use & JSON Schema

tools=[{"name": "record_invoice",
  "input_schema": {"type": "object",
    "properties": {
      "invoice_no": {"type": "string"},
      "due_date": {"type": ["string", "null"]},
      "category": {"enum": ["goods","services",
                            "other","unclear"]},
      "category_detail": {"type": ["string","null"]},
      "stated_total": {"type": "number"},
      "calculated_total": {"type": "number"},
      "conflict_detected": {"type": "boolean"}},
    "required": ["invoice_no", "stated_total"]}}],
tool_choice={"type": "tool", "name": "record_invoice"}
  • Schema eliminiert Syntaxfehler, nicht semantische → Summen, Datumsplausibilität im Code prüfen.
  • Required + nicht-nullable für evtl. fehlende Infos → Fabrikation. Nullable/optional verwenden.
  • Enums mit "other" + Detail-String und "unclear"; Normalisierungsregeln (Datumsformat, Währung) festlegen.
  • Nur „antworte in JSON" im Prompt reicht für Downstream-Integration nicht.

4.4 Validation, Retry & Feedback

  • Retry mit Dokument + fehlerhaftem Output + konkretem Validierungsfehler (ohne Fehler → derselbe Fehler).
  • Retries helfen nicht, wenn die Info nicht im Dokument steht → Retries deckeln, an Human Review routen.
  • Self-Check-Felder: calculated_total vs. stated_total, conflict_detected. Abweichung flaggen, nicht stillschweigend überschreiben.
  • detected_pattern-Felder, um abgelehnte Findings systematisch zu analysieren.

4.6 Multi-Instance & Multi-Pass Review

  • Selbst-Review in derselben Session = Selbstbestätigung (Reasoning des Generators im Kontext) → unabhängige Instanz.
  • Pro Datei lokal + Cross-File-Integrationspass statt ein Mega-Pass (ungleichmäßige Tiefe).
  • Confidence-Selbstauskunft nur zum Routen von Reviews – Schwellen erst auf gelabelten Daten validieren, nie unkalibriert auto-approven.

D5 Context Management & Reliability 15 %

5.1 Kritischen Kontext erhalten

  • Progressive Summaries verlieren Zahlen, Daten, Zusagen → persistenter Case-Facts-Block (Beträge, Daten, Bestell-IDs, Commitments) wörtlich außerhalb der zusammengefassten History.
  • Lost in the Middle: Kernbefunde an den Anfang, Section Headers in langen Inputs.
  • Tool-Output trimmen auf benötigte Felder, bevor er sich ansammelt.
Falle„Modell mit größerem Kontextfenster" – verschiebt das Problem nur; Summaries verlieren weiter Zahlen, die Mitte wird weiter vernachlässigt.

5.2 Eskalation & Mehrdeutigkeit

Eskalieren beiNicht (allein) bei
Expliziter Bitte um Menschen (sofort!), Policy-Lücke/Ausnahme, kein FortschrittSentiment/Frust-Score (misst Stimmung, nicht Bedarf), selbstberichteter Confidence

Mehrdeutiger Treffer (zwei „J. Smith") → nach Identifikator fragen (E-Mail, Bestellnr.), nie den wahrscheinlichsten raten.

5.3 Fehlerweitergabe in Multi-Agent-Systemen

  • Subagent liefert strukturierten Fehlerkontext: Fehlertyp, versuchte Query, Teilergebnisse, Alternativen.
  • Nie als leeren Erfolg unterdrücken (falsche Schlüsse ohne Signal); nie alles wegen eines Fehlers abbrechen (verwirft valide Arbeit); keine rohen Stacktraces.
  • Coordinator: andere Quelle/Retry versuchen, sonst Coverage-Lücke im Report annotieren.

5.4 Kontext in großen Codebases

  • Degradation in langen Sessions erkennen (widersprüchliche/vergessene Details).
  • Scratchpad-Dateien mit Findings; verbose Exploration an Subagents delegieren.
  • Vor Phasenwechsel zusammenfassen; /compact bewusst an Phasengrenzen mit Anweisung, was erhalten bleibt.
  • Crash-Recovery-Manifeste (Fortschritt, erledigte Dateien) für lange Läufe.

5.5 Human Review & Confidence-Kalibrierung

  • Aggregierte Accuracy versteckt Schwächen (97 % gesamt, aber 70 % bei handschriftlichen Formularen) → pro Dokumenttyp und Feld messen, bevor Review reduziert wird.
  • Stratifizierte Stichproben (seltene, fehleranfällige Segmente) statt einfacher Zufallsstichprobe.
  • Feld-Confidence-Schwellen auf gelabeltem Validierungsset kalibrieren.

5.6 Provenance & Unsicherheit

  • Claim → Quelle (URL/Dokument, Auszug, Datum) muss Zusammenfassungen überleben.
  • Widersprüchliche Werte: beide behalten, mit Quelle annotieren – nicht einen auswählen; unterschiedliche Daten/Methoden erklären.
  • Veröffentlichungs- und Erhebungsdatum mitführen; Inhaltstypen passend darstellen (Tabelle für Zahlen, Prosa für Erklärungen).

Prüfungstaktik

  • Zeit: 2 Min/Item → nach 60 Min ≈ Frage 30. Schwere Items flaggen, weiter, am Ende zurück.
  • Szenario-Kontext lesen: welche Tools, welche Constraints (Geld? Compliance? Latenz? Team vs. persönlich?).
  • Eliminieren: nur Prompt bei Garantie-Anforderung · überdimensioniert (Klassifikator, Fine-Tuning, größeres Modell/Kontext) · stiller Fehler · am Root Cause vorbei.
  • Keine Frage leer lassen. Bereit bei stabil ≥ 80 % in vollen Mocks über verschiedene Szenario-Ziehungen; offizielle Practice Exam auf der Academy machen.
