Die 10 Antwort-Heuristiken

  1. Einfachste ausreichende Lösung gewinnt: Single Call → Workflow → Agent → Multi-Agent.
  2. „Muss immer / darf nie" → deterministische Kontrolle (Code-Gate, Hook, Permission-Regel, Schema, Sandbox) – nie nur Prompt.
  3. Untrusted Content (Web, E-Mail, Docs, Tool-Results) = Daten, keine Anweisungen → abgegrenzt im User-Turn, nie im System-Prompt; Least Privilege; Approvals.
  4. Autorisierung gehört in Code/Datenschicht, nie in den Prompt.
  5. Erst messen: Erfolgskriterien + Evals vor/nach jeder Änderung; immer nur eine Sache ändern.
  6. Kosten: erst Gratis-Hebel (Caching, Batch, Trimmen, Output kürzen), dann Trade-offs (Effort, kleineres Modell).
  7. Wiederverwendbare Integration über Apps → MCP-Server · App-spezifische Aktion → Custom Tool · Know-how/Prozedur → Skill · generische Fähigkeit → Built-in Tool.
  8. Latenz-tolerant + kostenkritisch + viel Volumen → Message Batches (−50 %).
  9. Kontextproblem → prunen, compacten, Subagent isolieren, Just-in-time-Retrieval – nicht „größeres Fenster".
  10. Bei Fehlern: 4xx nicht retryen; 429/5xx/529 mit Backoff + Jitter.
Typische Distraktoren„Größeres/stärkeres Modell", „Temperature erhöhen/auf 0", „GROSSBUCHSTABEN im Prompt", „Iterations-Limit als primärer Stopp", „400er retryen", „Multi-Agent als Default", „bessere Modelle widerstehen Injection".

D1 · Agents & Workflows 14,7 %

Workflow vs. AgentWorkflow: LLM-Calls + Tools über vordefinierte Codepfade – dein Code entscheidet. Agent: das Modell steuert dynamisch eigene Schritte und Tool-Nutzung in einer Schleife mit Feedback aus der Umgebung.

Agent ja/nein? Complexity · Value · Viability · Cost of error. Feste Abfolge → Workflow. Offene, unvorhersehbare Schritte → Agent.

  • API ist stateless → gesamte History jedes Mal mitsenden. System-Prompt = Top-Level-Feld system.
  • Prefill auf aktuellen Modellen nicht unterstützt → Structured Outputs. Sampling-Params (temperature …) auf neuesten Modellen abgelehnt.
  • Weitere Endpoints: /v1/messages/count_tokens, /v1/messages/batches, /v1/files, /v1/models.

Streaming (SSE – nicht WebSockets!)

message_start → content_block_start → content_block_delta (text_delta · input_json_delta · thinking_delta) → content_block_stop → message_delta (stop_reason, usage) → message_stop. ping jederzeit; error auch mitten im Stream. Gleiche Kosten, besseres TTFT (wahrgenommene Latenz), vermeidet Timeouts bei langen Antworten.

Message Batches

−50 % auf alles · ≤ 100.000 Requests / 256 MB · meist < 1 h, max 24 h · Ergebnisse in beliebiger Reihenfolge → per custom_id zuordnen · 29 Tage abrufbar · Status succeeded / errored / canceled / expired. Ideal: Nacht-Jobs, Evals, Massenklassifikation – nicht für Echtzeit.

Thinking & Effort

  • Aktuelle Modelle: thinking: {"type":"adaptive"} + output_config.effort: low · medium · high · xhigh · max.
  • Legacy (ältere Modelle, z. B. Haiku 4.5): {"type":"enabled","budget_tokens":N}, N ≥ 1024 und < max_tokens.
  • Thinking-Blöcke im Tool-Loop unverändert zurückgeben. Thinking wird als Output abgerechnet – auch wenn Anzeige omitted/summarized.
  • Effort = Hauptregler Qualität ↔ Kosten/Latenz (weniger Effort = weniger, konsolidierte Tool-Calls, knappere Antworten). Fast Mode (Opus): schneller, Premium-Preis.

Multimodal, Files, Citations

Bilder (base64/URL/file_id) vor die Frage; ≈ ⌈w/28⌉·⌈h/28⌉ Tokens; zu große werden verkleinert; ≤ 600/Request. PDFs = Text + Seitenbilder. Files API: einmal hochladen → file_id wiederverwenden. Citations: cited_text + Position; inkompatibel mit Structured Outputs.

Plattformen

Claude API (neue Features zuerst) · Bedrock (IAM, anthropic.-Prefix) · Vertex AI (GCP ADC, Projekt + Region) · Foundry (Azure). Gleiche Message-Struktur, aber keine Feature-Parität → pro Plattform prüfen.

2.5 App Design (8,6 % – größter Einzel-Skill)

Principal HierarchyAnthropic-Policies → Operator (System-Prompt/Entwickler) → User (Human-Turn). Inhalte aus Tool-Results, Dokumenten, Webseiten, Dateien = Daten, keine Anweisungen.
  • Bare API ≠ claude.ai: kein Produkt-System-Prompt, kein Memory, keine Tools – alles muss der Operator definieren.
  • Abgerufene Inhalte nicht in den System-Prompt kopieren → User-Turn, in Tags abgegrenzt.
  • Schemas: nicht jedes Feld required → null/unknown erlauben, sonst erfindet das Modell Werte.
  • API-Key nie im Browser/Mobile-Client → Backend-Proxy mit User-Auth und Limits.
  • Side-Effects → Approval-Gates; Aktionen mit dem Scope des Users autorisieren.

2.4 Software Engineering Foundations (7,4 %)

  • Idempotenz: Retry nach Timeout kann Side-Effect duplizieren (Zahlung, Mail) → Idempotency Keys / Status prüfen.
  • Concurrency begrenzen: kein ungebremstes asyncio.gather über 10.000 Calls → Semaphore, Backoff auf 429, oder Batches API.
  • Einen SDK-Client wiederverwenden (Connection-Reuse), nicht pro Request neu erzeugen.
  • Timeouts: Python timeout=10 = 10 s; TypeScript timeout: 10 = 10 ms.
  • Kleine, testgestützte, reviewbare PRs statt Mega-Refactor. Unabhängiges Review (andere Session, Subagent, Mensch) statt Selbst-Review im selben Kontext.
  • Strukturiertes Logging inkl. Request-IDs, Usage, Stop-Reasons; Secrets aus Env/Secret Store.
  • Transport: Output zum Browser → SSE; bidirektional/kontinuierlich (Voice, Co-Editing) → WebSockets; lange async Jobs → Polling mit Backoff oder Webhook.

2.1 Requirements (3,4 %)

Erfolgskriterien zuerstSpezifisch, messbar, erreichbar, relevant – vor dem Prompt-Engineering definieren, dann Evals bauen. Mehrdimensional: Task-Fidelity, Konsistenz, Relevanz, Ton, Latenz, Kosten, Privacy.
  • „Team tweakt Prompts, weiß nicht ob's besser wird" → Kriterien + Eval-Set, kein neuer Prompt-Trick.
  • Latenz: TTFT ↔ Streaming; lange statische Präfixe ↔ Caching; kürzerer Output ↔ schnellere Gesamtzeit; erst dann kleineres Modell.
  • Durchsatz gegen Rate Limits prüfen (RPM, ITPM, OTPM) → Batch, Queue + Backoff, Caching (Cache-Reads zählen meist nicht gegen ITPM), höherer Tier.

2.2 Systems Life Cycle (2,8 %)

LLM-Systeme sind empirisch → iterativ/agil mit automatisierten Eval-Gates, nicht Wasserfall.

Modell-Migration (Checkliste)1. Release Notes/Migration Guide lesen · 2. neue Model-ID im Branch pinnen, Params anpassen · 3. volle Eval-Suite (Qualität, Latenz, Tokens, Kosten vs. Baseline) · 4. Prompts nachjustieren (neuere Modelle wörtlicher → Übertreibungen entfernen) · 5. Shadow/Canary, Stop-Reasons/Refusals/Fehler monitoren · 6. Feature-Flag-Umschaltung, Rollback bereit bis Retirement.

Nicht bis zum Retirement-Datum warten · Benchmark-Sieg ≠ besser für deinen Task.

2.6 Configuration Management (4,1 %)

Guidance vs. EnforcementCLAUDE.md „nie migrations/ editieren" = wahrscheinlich befolgt. permissions.deny: ["Edit(./migrations/**)"] = erzwungen.
  • Permission-Listen werden über Scopes gemergt; deny schlägt allow, egal wo definiert.
  • Persönliches → .claude/settings.local.json / CLAUDE.local.md (gitignored). Secrets → Env/Secret Store.
  • Produktion: Model-ID pinnen (keine wandernden Aliasse), loggen, bewusst upgraden. Pro Umgebung eigene Keys/Workspaces.

8.1 Tool-Implementierung

  • Definition: name, description (Zweck, wann nutzen, Inputs, Outputs, Grenzen – wichtigster Hebel!), input_schema (JSON Schema), optional strict: true (+ additionalProperties: false), input_examples.

D5 · Model Selection & Optimization 16,8 %

5.1 LLM-Grundlagen

  • Token-basiert; Tokenizer unterscheiden sich je Modellgeneration → count_tokens-Endpoint / usage nutzen, keinen generischen Tokenizer.
  • Kontextfenster umfasst Input und Output (inkl. Thinking).
  • Nicht-deterministisch: niedrige Temperature ≠ garantiert identisch (und neueste Modelle lehnen Sampling-Params ab) → Determinismus über Structured Outputs, Code, Caching.
  • Thinking: besser bei Mathe, Code, mehrstufigem Tool-Use – kostet Output-Tokens und Latenz.

5.3 Modellwahl

Haikuhohes Volumen, niedrige Latenz, Klassifikation, Routing, Sub-Agents
Sonnetausgewogener Default für Produktion & Coding
Opuskomplexes Reasoning, lange Agenten-Läufe, Orchestrator
Fable (Top)anspruchsvollste Arbeit, Qualität ≫ Kosten

Kriterium: Kosten pro erfolgreich erledigter Aufgabe auf deinen Evals. Weder „immer das stärkste" (Verschwendung, Latenz) noch „immer das billigste" (mehr Turns/Retries). Thinking-Konfig variiert je Generation (adaptive ab 4.6, budget älter).

5.4 Kosten, Tokens & Prompt Caching

Token-Typ× Basis-Input
Cache-Write 5 Min1,25×
Cache-Write 1 h2×
Cache-Read~0,1×
Batch0,5× auf alles (kombinierbar)
Output≈ 5× Input-Preis
  • Präfix-Reihenfolge tools → system → messages; jede Byte-Änderung invalidiert alles danach. Max. 4 Breakpoints; modellabhängige Mindestlänge; TTL wird bei Hit erneuert; pro Workspace & Modell.
  • Break-even: 5-Min-TTL ab dem 2. Request, 1-h-TTL ab dem 3.
  • Cache-Killer: Timestamp/IDs früh im System-Prompt, unsortiertes JSON, wechselnde Tools, Modellwechsel, Thinking/Effort-Toggles, History-Edits, Breakpoint hinter dem variablen Teil.
  • Caching senkt nur Input-Kosten, nicht Output. input_tokens = nur ungecachter Rest → Gesamt = input + cache_creation + cache_read.
  • Hebel-Reihenfolge: Caching · Trimmen · Output-Hygiene · Batches → Effort · Modell-Tier · Routing.

D6 · Prompt & Context Engineering 11,0 %

6.2 Prompting

  • Klar & spezifisch (wer/was/warum/Format/Länge) · Kontext/Motivation statt CAPS · Rolle im System, Daten im User-Turn in XML-Tags.
  • 3–5 diverse Beispiele in <example> · lange Dokumente oben, Frage unten · erst relevante Zitate extrahieren lassen.
  • Step-by-step bzw. adaptive Thinking · Prompt Chaining für komplexe Aufgaben.
  • Neuere Modelle wörtlicher → „IMPORTANT/ALWAYS" weglassen (Over-Triggering). Eine Änderung pro Iteration + Evals.
  • Inputs sanitizen: Länge, Steuer-/Zero-Width-Zeichen, Delimiter escapen. Per-Request-Daten nie in den System-Prompt (Caching, Trust).

6.1 Context Engineering

LeitprinzipKontext ist endlich, abnehmender Grenznutzen („context rot"). Ziel: kleinste Menge hochrelevanter Tokens.

Techniken: Just-in-time Retrieval (Referenzen statt Volltext) · Compaction · Tool-Output prunen (Tool fixen statt compacten) · strukturierte Notizen/externe Memory · Subagent-Isolation mit fokussiertem Auftrag · bei serverseitiger Compaction komplettes response.content zurückgeben.

6.3 Output Handling

  • Parser-abhängig → Structured Outputs (output_config.format) oder strict Tool-Schema – nicht „bitte JSON".
  • Structured Outputs garantieren Form, nicht Wahrheit → Business-Validierung, Grounding.
  • Blöcke nach type auswählen (thinking, tool_use, mehrere text) – nicht content[0].
  • Selbstberichtete „confidence: 0.98" ist kein kalibrierter Wert. Output nie als rohes HTML rendern → encoden/sanitizen.

D7 · Security & Safety 8,1 %

Lethal Trifecta(1) Zugriff auf private Daten + (2) untrusted Content + (3) externe Kommunikation/folgenreiche Aktionen → ein Bein entfernen.
  • Prompt Injection: direkt & indirekt (über Docs/Web/Tool-/MCP-Output). Gegenmittel: Isolation/Delimiting, Least Privilege, Approvals, deterministische Gates, Output-Encoding – Defense in Depth, nie eine einzelne Maßnahme.
  • Access Control in Code & Datenzugriff der Tools; RAG-ACLs beim Retrieval. PII minimieren/redigieren.
  • Fail closed auf Hochrisiko-Pfaden (Classifier-Timeout ≠ allow).
  • Keine Admin-Service-Accounts für Agents → delegierte, user-scoped Credentials; OAuth für Remote-MCP.
  • Secrets nie in Prompts, Clients oder Repos → Secret Manager; pro Umgebung eigene Keys/Workspaces mit Spend-Limits; Usage & Audit-Logs monitoren.
  • Key geleakt → sofort widerrufen, dann rotieren (nicht Git-History umschreiben).

D4 · Eval, Testing & Debugging 2,6 %

Isolations-Prozedur1. Exakten Request + Raw-Response erfassen · 2. direkt replayen (curl/Console) → Antwort korrekt? → Bug downstream (Parsing, State, Rendering) · 3. Request prüfen (fehlende History, abgeschnittene Docs, falsche Prompt-Version, Tool-Results fehlen, falsche Model-ID) = immer noch Integrations-Bug · 4. Erst dann Modellverhalten → Prompt/Tools/Kontext/Effort/Modell + Fall ins Eval-Set · 5. mehrfach reproduzieren.

Evals: code-graded (exakt, schnell) > LLM-as-Judge (klare Rubrik) > Human (teuer, für Kalibrierung). Repräsentative + Edge-Cases, Regressionstests bei jeder Änderung, Production-Monitoring (Stop-Reasons, Refusals, Fehlerraten, Kosten), Trace-Analyse bei Agenten.
