# Domain 8 — Tools and MCPs

### d8-tool-01
skill: 8.1
type: single
An agent has two tools, `get_data` ("Gets data") and `fetch_info` ("Fetches info"). Claude frequently picks the wrong one. What is the most effective fix?
- [ ] Add a third tool that decides which of the two existing tools to call for each request
- [x] Rename both descriptively and describe what each returns and when to use which
- [ ] Force one of the tools with `tool_choice` on every request to avoid ambiguity
- [ ] Raise the effort level to max so the model reasons longer about tool choice
> Claude selects tools based on names and descriptions. Vague, overlapping definitions cause wrong selections; precise when-to-use guidance fixes them.

### d8-tool-02
skill: 8.1
type: single
A tool call fails because the external API returned "404 order not found". How should the harness respond?
- [ ] Raise an exception and end the conversation with a generic error message
- [ ] Return an empty `tool_result`, so Claude assumes no order data exists
- [x] Return an `is_error` result with guidance, e.g. the expected ID format
- [ ] Retry the call silently ten times before giving up on the lookup
> Error results with guidance let Claude recover gracefully. Exceptions break the loop, empty results invite hallucination, and blind retries don't fix a permanent error.

### d8-tool-03
skill: 8.1
type: single
A support agent can issue refunds via a tool. Policy says a human must approve every refund. What is the best implementation?
- [ ] Instruct Claude in the system prompt to always ask the user before issuing a refund
- [x] Gate the tool in the harness: show the proposed call to a human, execute only on approval
- [ ] Remove the refund tool and let Claude describe the refund steps to the user in text
- [ ] Use `tool_choice: none` for every conversation that mentions refunds
> Approval must be enforced by the harness (human-in-the-loop) rather than relying on the model to ask. Removing the tool loses functionality.

### d8-tool-04
skill: 8.1
type: single
What distinguishes server-side tools (e.g., web search, code execution) from client-side tools?
- [ ] Server tools require you to write and host the execution code yourself
- [x] Anthropic runs server tools in the request; your app runs client tools
- [ ] Client tools are only available inside Claude Code, not through the API
- [ ] Server tools cannot be configured, for example with domain filters
> With server tools you declare them and the API runs them, returning result blocks; client tools are executed by your harness. Server tools accept configuration such as max uses or domain filters.

### d8-tool-05
skill: 8.1
type: multi
Which TWO practices produce a better tool set for an agent?
- [x] Merge operations that always occur together into one task-oriented tool
- [ ] Expose every endpoint of the internal REST API as its own separate tool
- [x] Return concise results with readable identifiers and pagination hints
- [ ] Return the raw API payloads so Claude always has all available data
- [ ] Use very short tool names like `t1` and `t2` to save input tokens
> Fewer, task-shaped tools and token-efficient results improve selection and context usage. Thin wrappers over every endpoint and raw payloads do the opposite.

### d8-tool-06
skill: 8.1

Claude returns three `tool_use` blocks for independent lookups. How should the harness handle them?
- [ ] Execute only the first call and let Claude request the others in later turns
- [x] Execute them (concurrently if safe) and return all results in one user message
- [ ] Return each result in its own assistant message, in the order they finish
- [ ] Ask Claude to resend the calls one at a time in separate responses
> Parallel tool calls should be answered together in one user message, each matched by `tool_use_id`.

### d8-tool-07
skill: 8.1
type: single
What does setting `strict: true` on a custom tool guarantee?
- [ ] That Claude will call this tool on every request where it is defined
- [x] That the tool `input` Claude provides validates against the tool's schema
- [ ] That the tool executes faster because the input is pre-validated
- [ ] That the tool's output is validated before it is returned to Claude
> Strict tool use guarantees schema-valid arguments (the schema needs `additionalProperties: false`). It doesn't force usage or validate your outputs.

### d8-tool-08

An enterprise agent would need 300 tool definitions across many systems, bloating every request. Which approach best addresses this?

### d8-tool-10

### d8-tool-11

### d8-tool-12
skill: 8.1
type: single
A user declines an action that Claude proposed via a tool call. What should the harness send back?
- [ ] Nothing; just remove the `tool_use` block from the conversation history
- [x] A `tool_result` for that `tool_use_id` saying the user declined
- [ ] An HTTP error status that tells the API the call was rejected

> Every tool_use needs a matching result; a "declined" result keeps the conversation valid and informs the model.

### d8-mcp-01
skill: 8.2
type: single
A team needs Claude to call an internal inventory service exposed as a REST API. They want the capability to be reusable across several Claude applications and maintained independently of any one app. Which approach best fits?
- [ ] Hard-code the inventory logic into each application's system prompt.
- [x] Build an MCP server that exposes the inventory operations as tools so multiple Claude applications can connect to it.
- [ ] Paste the current inventory data into the context window on every request.
- [ ] Rely on a built-in tool, since built-in tools can reach any internal REST API.
> An MCP server exposes reusable tools that multiple Claude applications can share and that can be maintained independently. Hard-coding logic into prompts is neither reusable nor maintainable; pasting data gives no live access and wastes context; built-in tools do not automatically reach arbitrary internal APIs. (Official sample question 3, reproduced as published.)

### d8-mcp-02
skill: 8.2
type: single
A developer's stdio MCP server works in tests but Claude Code reports parse errors when connecting. The server prints debug messages with `print()`. What's wrong?
- [ ] stdio servers must listen on port 443 and cannot print to the console at all
- [x] In stdio transport, stdout carries protocol messages; debug output belongs on stderr
- [ ] The server must use a WebSocket transport whenever it produces log output
- [ ] Python's `print()` is not supported inside MCP server processes
> Writing non-protocol text to stdout corrupts the message stream. Log to stderr or a file.

### d8-mcp-03
skill: 8.2
type: single
Which MCP primitive is **application-controlled** and intended for read-only, URI-addressed context such as a database schema?
- [ ] Tools
- [x] Resources
- [ ] Prompts
- [ ] Elicitation
> Resources provide context data the host decides to include. Tools are model-controlled actions; prompts are user-controlled templates.

### d8-mcp-04
skill: 8.2
type: single
An MCP server will be hosted centrally and used by hundreds of employees' Claude clients over the network. Which transport and auth approach fits?
- [ ] stdio, with a shared password passed on each client's command line
- [x] Streamable HTTP with OAuth-based authorization over TLS
- [ ] stdio tunneled over SSH, with one SSH account per employee
- [ ] Streamable HTTP without authentication, because the server is internal
> Remote, multi-client servers use Streamable HTTP; MCP recommends OAuth for authorization. stdio is a local subprocess transport.

### d8-mcp-05
skill: 8.2

What is the relationship between MCP hosts, clients and servers?
- [ ] One MCP client connects to many servers at once over a shared connection
- [x] The host creates one client per server; each client holds one dedicated connection
- [ ] Servers connect to each other directly and share tools across the network
- [ ] The MCP server hosts the language model that the client application uses
> Host → many clients → each with one server connection. Servers don't host the model.

### d8-mcp-07

Which TWO are valid ways to make an MCP server available to Claude?
- [x] Claude Code: `claude mcp add` or a project `.mcp.json` (stdio or HTTP)
- [x] The Messages API MCP connector: `mcp_servers` plus an `mcp_toolset` tool entry
- [ ] Uploading the server's source code as an attachment in a user message

### d8-mcp-08
