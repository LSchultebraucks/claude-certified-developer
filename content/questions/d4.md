### d4-dbg-01
skill: 4.1

A support bot returns perfect answers when the team pastes the logged request JSON into a test script, but users see garbled answers in the app. Where is the problem most likely?
- [ ] In the model's reasoning, which behaves differently under production load
- [x] In the integration layer after the API response: parsing, encoding or rendering
- [ ] In Anthropic's rate limiting, which degrades answers when limits are approached
- [ ] In the system prompt, which is interpreted differently by the production model
> Replaying the exact request yields a correct response, so the model output is fine; the defect is in how the app processes or displays it.

### d4-dbg-02
skill: 4.1
type: single
During a traffic spike, many requests fail with HTTP 529 `overloaded_error`. What is the most appropriate recovery strategy?
- [ ] Fix the request payload, since 529 indicates a malformed or oversized request body
- [x] Retry with exponential backoff and jitter; if it persists, fall back or queue work
- [ ] Rotate the API key, since 529 indicates that the key's quota has been revoked
- [ ] Retry immediately in a tight loop until the request succeeds, to keep latency low
> 529 is transient overload. Backoff with jitter avoids amplifying load; fallbacks and queueing provide graceful degradation. It's not a payload or credential issue.

### d4-dbg-03
skill: 4.1

An agent trace shows Claude calling `search_web` for questions about internal HR policies, although a `search_policies` tool exists. Both descriptions are one line long. What is the best first fix?
- [ ] Remove the web search tool permanently so the policy tool is the only option left
- [x] Rewrite both descriptions to state what each covers and when (not) to use it
- [ ] Increase `max_tokens` so the model has more room to compare the two tools
- [ ] Retry the request automatically until the policy search tool is selected
> Tool selection is driven by descriptions. Vague or overlapping descriptions cause wrong-tool failures; precise "when to use" guidance fixes them. Removing a useful tool or retrying doesn't address the cause.

### d4-dbg-04
skill: 4.1
type: single
A request fails with HTTP 404 `not_found_error` immediately after a deploy. The message starts with `model:`. What is the most likely cause?
- [ ] The API is overloaded and temporarily cannot serve the requested model
- [x] The model ID is misspelled or not available to the organization
- [ ] The prompt exceeds the model's context window after the deploy
- [ ] The API key was invalidated by the deploy and must be regenerated
> A 404 referencing the model indicates an unknown or unavailable model ID (e.g., a typo like dots instead of hyphens). Invalid keys produce 401; overload produces 529; too-long input produces 400/413.

### d4-dbg-05
skill: 4.1
type: single
Structured JSON output fails to parse only for long reports; short reports work fine. What should you check first?
- [ ] Whether the model is hallucinating additional fields in longer reports
- [x] Whether `stop_reason` is `max_tokens`, meaning the output was truncated
- [ ] Whether the API key's rate limit is lower for long responses
- [ ] Whether prompt caching corrupts responses that exceed a certain size
> Length-dependent parse failures are the signature of truncation. Check `stop_reason` and raise `max_tokens` or shorten the requested output.

### d4-dbg-06
skill: 4.1
type: single
A model response arrives with HTTP 200 and `stop_reason: "refusal"`. What should the application do?
- [ ] Execute the tool calls contained in the response and continue the loop normally
- [ ] Treat it as a network error and keep retrying the same request with backoff
- [x] Skip that turn's tools and partial content; show a fallback or route to a human
- [ ] Parse the refusal text as the final answer and display it as a normal reply
> A refusal is a safety decline delivered as a normal response. Don't execute tools from that turn; handle it explicitly with a fallback path.

### d4-dbg-07
skill: 4.1
type: multi
Which TWO errors should a Claude API client **not** retry automatically?
- [x] 400 `invalid_request_error`
- [ ] 429 `rate_limit_error`
- [x] 401 `authentication_error`
- [ ] 529 `overloaded_error`
- [ ] 500 `api_error`
> 400 and 401 are client errors that require fixing the request or credentials. 429, 500 and 529 are transient and should be retried with backoff.

### d4-dbg-08
skill: 4.1

An agent repeatedly calls `get_invoice` with the same invalid ID. Each time, the tool returns an empty string. What change most directly breaks the loop?
- [ ] Add a stop sequence that ends generation when the invoice tool name appears
- [x] Return an informative `is_error` result explaining the problem, plus an iteration cap
- [ ] Lower the temperature so the model chooses a different ID on the next attempt
- [ ] Remove the invoice tool from the request after its first unsuccessful call
> Uninformative results give Claude nothing to adapt to. Actionable error messages let it change course; caps protect against runaway loops.

### d4-dbg-09
skill: 4.1
type: single
Which is the most reliable way to handle API errors in Python SDK code?
- [ ] Catch `Exception` and check whether the message text contains words like "rate"
- [x] Catch typed SDK exceptions from most to least specific and branch on retryability
- [ ] Wrap every call in a bare `except:` and continue silently when a call fails
- [ ] Check only whether the HTTP status is 200 and treat everything else the same
> Typed exceptions preserve the distinction between error classes; string matching on messages is brittle and broad catch-alls hide bugs.

### d4-dbg-10
skill: 4.1
type: single
Your team relies on an LLM-as-judge to grade answer helpfulness in evals. What practice increases trust in its scores?
- [ ] Use the same small model that produced the answers as the judge, without extra checks
- [x] Calibrate it against human-graded samples, use a clear rubric, reason before scoring
- [ ] Ask the judge for a bare 1–10 score with no criteria, to avoid biasing it
- [ ] Run each case exactly once and treat the resulting score as a precise measurement
> LLM judges should be calibrated against human labels and given explicit rubrics; reasoning before the verdict improves consistency. Because outputs vary, aggregate over multiple cases/samples.
