# Domain 1 — Agentic Architecture & Orchestration

### a1-loop-01
skill: 1.1
scenario: S1
Your support agent sometimes replies "Let me look up your order now." and the conversation ends without any lookup. The API response for that turn has `stop_reason: "tool_use"` and contains a text block followed by a `tool_use` block. Your loop exits as soon as the response contains a text block. What is the correct fix?
- [ ] Add a system-prompt instruction telling Claude never to write text in the same turn as a tool call
- [x] Drive the loop by `stop_reason`: execute tools and continue on `tool_use`, exit only on `end_turn`
- [ ] Raise the loop's iteration limit so that the agent has more turns available to finish its work
- [ ] Parse the text block for phrases like "let me" and treat those as a signal to keep looping
> `stop_reason` is the contract for loop control. Claude often explains its next step in text alongside a `tool_use` block; exiting on text skips the requested call. Prompting Claude not to write text is fragile and unnecessary, the iteration limit is irrelevant (the loop exits after one turn), and phrase parsing is exactly the natural-language anti-pattern to avoid.

### a1-loop-02
skill: 1.1
scenario: S4
A developer-productivity agent repeats the same Grep calls and contradicts conclusions it reached earlier. The loop sends `[original task, latest tool result]` on each iteration to save tokens. What is the root cause?
- [ ] The model's temperature is too high, so its tool choices vary randomly from one iteration to the next
- [ ] The Grep tool's description is too vague, so the model cannot tell when a search has already been done
- [x] Earlier assistant turns and tool results are dropped, so Claude has no record of what it already did
- [ ] The agent lacks a scratchpad tool, which is required for any agent that runs more than a few iterations
> Each iteration must append the full assistant turn and the tool results to the history; that is how Claude knows what it has done. Rebuilding the prompt from the task plus the latest result throws that away, causing repeated calls and contradictions. Context size should be managed deliberately (trimming, summaries of facts), not by discarding the loop's own history.

### a1-loop-03
skill: 1.1
scenario: S3
Your research agent's loop stops when it reaches 10 iterations, and reports the current text as the final answer. Reviewers notice reports that end mid-investigation. What is the best change?
- [ ] Increase the limit to 25 iterations so that complex research requests have enough turns to finish
- [ ] Ask Claude in the system prompt to always wrap up its research within ten tool calls at the most
- [ ] Remove the limit entirely, since `stop_reason` already guarantees that the loop will eventually terminate
- [x] Keep a cap only as a safety net that flags the run as incomplete; treat `end_turn` as the completion signal
> An iteration cap is a guard against runaway loops and cost, not a completion signal. Reaching it means the run was cut off, which should be surfaced (raise, flag, log) rather than presented as a finished report. Raising the number just moves the problem; prompting for brevity degrades quality; removing the cap entirely loses protection against loops that never reach `end_turn`.

### a1-loop-04
skill: 1.1
scenario: S6
An extraction agent occasionally returns a JSON object that is cut off mid-string, and your loop passes it downstream as the final answer. The response for those cases shows `stop_reason: "max_tokens"`. What should the loop do?
- [x] Treat `max_tokens` as an incomplete response: raise the token limit or continue generation, never accept it as final
- [ ] Treat `max_tokens` like `end_turn`, but repair the truncated JSON with a lenient parser before passing it on
- [ ] Retry the identical request immediately, since the truncation is a transient failure of the API service
- [ ] Switch to a larger-context model, because the context window was exceeded during the extraction call
> `max_tokens` means output hit the configured output limit, so the result is truncated. The loop must handle it explicitly by increasing `max_tokens` or continuing. Repairing truncated JSON silently loses data; retrying the same request reproduces the truncation; the context window is a different limit (that would be `model_context_window_exceeded`).

### a1-loop-05
skill: 1.1
scenario: S1
In one turn Claude requests `get_customer` and `lookup_order` together. Your code executes `get_customer`, appends its result, and calls the API again, planning to run `lookup_order` later. The API returns an error. Why?
- [ ] The two tools must be declared as parallel-safe in their definitions before Claude may call them together
- [ ] Claude may only request one tool per turn, so the second tool call violated the API's tool-use contract
- [x] Every `tool_use` block in the assistant turn needs a matching `tool_result` in the next user message
- [ ] The `get_customer` result must be sent as an assistant message instead of being placed in a user message
> When Claude requests several tools in one turn, all of them must be answered — each `tool_result` with the matching `tool_use_id` — in the next user message. Claude is allowed to call multiple tools per turn; no "parallel-safe" declaration is required, and tool results go in user messages.

### a1-loop-06
skill: 1.1
scenario: S4
A tool call fails because a file path does not exist. Which handling gives the agent the best chance to recover?
- [ ] Raise an exception to stop the loop so that a developer can investigate the failure and restart the run
- [x] Return a `tool_result` with `is_error: true` and a message such as "File not found; similar: src/api/app.py"
- [ ] Return an empty string as the tool result, so the model notices that nothing useful came back from it
- [ ] Silently retry the same call three times before returning the last error to the developer's error logs
> Errors are information for the model: returned as an error result with a helpful message, Claude can correct its input or choose another approach. Aborting the loop gives up immediately; an empty string hides the failure; retrying a deterministic "not found" error wastes calls.

### a1-loop-07
skill: 1.1
scenario: S3
Which statement best describes how decisions are made inside a well-designed agentic loop compared with a workflow?
- [ ] In both designs the developer pre-configures the order of tool calls, and the model only fills in their parameters
- [ ] In the loop the model picks tools at random, while a workflow uses the model's judgement to pick each next step
- [ ] In a loop the developer must specify a decision tree in the system prompt that the model follows step by step
- [x] In the loop Claude chooses the next tool from the current context; a workflow follows steps fixed in code
> The defining property of an agent loop is model-driven decision making: Claude decides which tool to call next based on what it has observed. Workflows encode the sequence in code. Decision trees in prompts recreate a workflow less reliably; nothing about loops is random.

### a1-loop-08
skill: 1.1
scenario: S5
A CI agent that uses a server-side web-fetch tool sometimes returns a response with `stop_reason: "pause_turn"`. Your loop treats any stop reason other than `tool_use` as completion. What happens, and what is the fix?
- [ ] Nothing harmful happens; `pause_turn` is just an informational label that indicates a long but complete turn
- [x] The run ends unfinished; send the assistant content back unchanged in a new request so Claude can continue
- [ ] The tool failed permanently; return an error result for the fetch tool and let Claude choose another approach
- [ ] The rate limit was hit; wait for the time given in the retry-after header and then resend the original request
> `pause_turn` indicates a long-running server-tool turn was paused; it is not completion. Continue by sending the response back so Claude resumes. Treating it as done truncates the work. It isn't a tool failure or a rate limit (those surface as errors or HTTP 429).
