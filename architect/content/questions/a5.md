# Domain 5 — Context Management & Reliability

### a5-ctx-01
skill: 5.1
scenario: S1
In long support conversations, your agent summarises the history every 10 turns. Late in conversations it sometimes confirms the wrong refund amount or date that was agreed earlier. What is the best fix?
- [ ] Summarise less often, e.g. every 20 turns, so that fewer details are lost per summary
- [ ] Switch to a model with a larger context window so that summarisation is rarely needed
- [x] Keep a persistent case-facts block with exact amounts, dates and IDs, re-sent every turn
- [ ] Ask the summariser to "preserve all important details" when it condenses the history
> Progressive summaries drop exact values; a persistent, verbatim facts block keeps them. Less frequent summaries and bigger windows delay but don't prevent the loss; asking the summariser is unreliable.

### a5-ctx-02
skill: 5.1
scenario: S3
An aggregated research input of 80,000 tokens contains a key finding in the middle that the synthesis agent often overlooks. What change helps most?
- [x] Put a summary of key findings at the start and organise the rest under clear section headers
- [ ] Repeat the full input twice so that every finding appears in more than one position
- [ ] Remove the beginning and end of the input so that the middle becomes more prominent
- [ ] Ask the synthesis agent to read the input more carefully before writing its report
> The lost-in-the-middle effect is mitigated by placing key information at the start and structuring the input. Duplicating doubles cost; cutting content loses information; exhortation is weak.

### a5-ctx-04
skill: 5.1
scenario: S3
Subagents return long prose summaries, and the coordinator's context fills quickly, causing later results to be handled poorly. Which change helps most?
- [ ] Let subagents write directly into the final report so the coordinator never sees them
- [ ] Increase the number of subagents so each one returns a shorter summary on average
- [x] Have subagents return compact structured records with key facts and source metadata
- [ ] Ask the coordinator to forget earlier results once it has read the newer results
> Structured, compact results preserve facts while saving context. Bypassing the coordinator loses control; more subagents add overhead; models can't "forget" on request.

### a5-ctx-05
skill: 5.1
scenario: S1
Where should a support agent's case-facts block be maintained?
- [ ] Inside the model's own summary, which it updates whenever it notices a new fact
- [x] In application code that updates it from tool results and includes it in each request
- [ ] In the customer's messages, by asking them to restate key facts in every message
- [ ] In CLAUDE.md, so that the facts are loaded for every conversation with the agent
> Application-maintained state is reliable and verbatim. Model-maintained summaries can drift; customers shouldn't repeat facts; CLAUDE.md is for standing project instructions, not per-case data.

### a5-ctx-07
skill: 5.1
scenario: S3
Why is progressive summarisation especially risky for research involving statistics?
- [ ] Summaries are always longer than the original text, increasing token costs
- [ ] Summarisation removes all sources, so no citations can ever be recovered

### a5-esc-01

- [ ] Complete the address change quickly first, then offer to connect a human if still needed
- [ ] Explain that the agent can handle this request and ask the customer to give it a try
- [x] Escalate to a human immediately, passing a structured summary of the request

### a5-esc-03
skill: 5.2

A team proposes routing conversations to humans whenever sentiment analysis detects strong negative emotion. What is the main problem?
- [ ] Sentiment analysis requires a separate model, which adds latency to every conversation

- [ ] Customers with negative sentiment should never be escalated because humans are expensive

### a5-esc-04

### a5-esc-05

Which escalation trigger is the least reliable?

- [x] The agent's self-reported confidence falls below a fixed threshold

### a5-esc-07

### a5-prop-02
skill: 5.3
scenario: S3
One of five subagents fails after retries. Which coordinator behaviour is best?
- [ ] Abort the entire research run and report an error, since the result would be incomplete
- [ ] Ignore the failure and synthesise from the four successful results without mentioning it
- [x] Continue with the available results, try an alternative if possible, and annotate the coverage gap
- [ ] Restart all five subagents from the beginning so that the results are consistent
> Graceful degradation keeps valid work and states its limits. Aborting discards work; ignoring hides gaps; restarting everything wastes cost.

### a5-prop-03
skill: 5.3
scenario: S3
What should a subagent include when it propagates an unresolved failure to the coordinator?
- [ ] Only the exception class name, so that the coordinator's context stays as small as possible
- [x] The failure type, the attempted query, any partial results and possible alternative approaches
- [ ] The full stack trace and raw HTTP response, so the coordinator can debug the failure itself
- [ ] A recommendation to abort, since subagents know best whether the run can still succeed
> Structured context lets the coordinator decide on recovery. Bare names are too little; raw traces are noise; the coordinator decides, not the subagent.

### a5-prop-04
skill: 5.3
scenario: S4
A file-analysis subagent hits a permission error on one directory. Where should the decision about what to do next be made?
- [ ] In the subagent, which should silently skip the directory and continue with the others
- [ ] In the subagent, which should stop the whole system because permissions are critical
- [ ] In the tool, which should automatically elevate its permissions and retry the read
- [x] In the coordinator, after the subagent reports the error with context and partial results
> Non-recoverable errors propagate with context so the coordinator can choose (skip and annotate, escalate, request access). Silent skipping hides gaps; stopping everything overreacts; auto-elevation is unsafe.

### a5-prop-05
skill: 5.3
scenario: S3
Which errors should a subagent typically resolve locally before propagating?
- [x] Transient failures such as timeouts, which may succeed on retry with backoff
- [ ] Permission failures, by trying alternative credentials stored in its environment
- [ ] Business-rule violations, by adjusting the request until the rule no longer applies
- [ ] All errors, so that the coordinator never has to handle any failures at all
> Transient errors are good candidates for local retry. Permission and business errors should propagate; hiding all errors from the coordinator removes its ability to decide.
