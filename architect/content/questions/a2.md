# Domain 2 — Tool Design & MCP Integration

### a2-tool-01
skill: 2.1
scenario: S1
Your support agent frequently calls `get_customer` when customers ask about an order ("check my order #12345"). Both tools have one-line descriptions ("Retrieves customer information" / "Retrieves order information"). What is the most effective first step?
- [ ] Add five few-shot examples to the system prompt showing order questions routed to `lookup_order`
- [ ] Add a routing classifier that inspects each message and decides which tool should be offered to Claude
- [x] Expand both descriptions with purpose, input formats, example queries and when to use each versus the other
- [ ] Merge the two tools into a single `lookup` tool that accepts either a customer email or an order number
> Tool descriptions are the primary signal for tool selection; minimal, overlapping descriptions are the root cause. Rewriting them is low-effort and high-impact. Few-shot examples add tokens and don't fix the ambiguity; a classifier is over-engineered as a first step; merging tools hides the ambiguity in parameters.

### a2-tool-02
skill: 2.1
scenario: S3
A research agent has one tool, `analyze_document(doc, mode)`, where `mode` is "extract", "summarize" or "verify". It often picks the wrong mode. What is the best redesign?
- [ ] Keep the tool and list the three modes in the system prompt with a short explanation of each of them
- [x] Split it into `extract_data_points`, `summarize_content` and `verify_claim_against_source` with clear contracts
- [ ] Make `mode` optional and let the tool decide automatically which operation is the most appropriate one
- [ ] Add a fourth mode, "auto", that runs all three operations and returns every result to the agent at once
> Purpose-specific tools with precise inputs and outputs are selected and used more reliably than one generic tool with a mode switch. Prompt explanations don't fix the interface; letting the tool guess or running everything shifts the ambiguity and wastes work.

### a2-err-01
skill: 2.2
scenario: S1
Your `lookup_order` MCP tool returns `{"orders": []}` both when no orders exist and when the order database is unreachable. What is the main risk, and the fix?
- [ ] The agent will make too many tool calls; the fix is to cache empty results for a few minutes
- [ ] The agent's responses will be too slow; the fix is to add a shorter timeout to the database call
- [x] The agent treats an outage as "no orders"; return `isError: true` with a categorised error when lookup fails
- [ ] The model will hallucinate orders; the fix is to always return at least one placeholder order record
> Conflating failure with an empty result makes the agent act on false information. A failed lookup must be an error (with category and retryability), distinct from a successful empty result. The other options don't address the misrepresentation.

### a2-err-02
skill: 2.2
scenario: S1
`process_refund` fails because the refund exceeds policy. The tool returns `{"isError": true, "message": "Operation failed"}` and the agent retries three times. What should the error contain instead?
- [ ] A shorter message such as "Fail" so the model wastes fewer tokens on reading the error text
- [x] A business-error category, `isRetryable: false`, and a message explaining the limit and next step
- [ ] A transient-error category so that the agent waits a moment before trying the refund once again
- [ ] The full stack trace of the payment service so that the model can diagnose the underlying problem
> Structured errors with category and retryability let the agent respond correctly: business errors shouldn't be retried; explain or escalate. A generic message causes useless retries; mislabelling as transient makes it worse; stack traces are noise.

### a2-err-03
skill: 2.2
scenario: S3
Which error category should an agent normally retry without changing anything?
- [x] Transient errors such as timeouts or temporary service unavailability
- [ ] Validation errors such as a malformed date in the tool's input
- [ ] Business errors such as a request that violates a company policy
- [ ] Permission errors such as a caller not authorised for the resource
> Transient failures may succeed on retry (with backoff). Validation errors need corrected input; business and permission errors will fail again and need explanation or escalation.

### a2-err-04
skill: 2.2
scenario: S6
A schema-validation MCP tool rejects an extraction because `invoice_date` is "31/02/2026". What makes the error response most useful?
- [ ] A permission-error category, since the extraction was not authorised to write invalid data
- [ ] A transient-error category, so the agent retries the identical validation call a few times
- [ ] An empty success response, so the pipeline continues and a human fixes the date later on
- [x] A validation-error category naming the field and problem, so Claude can re-check and correct it
> Validation errors are recoverable by correcting the input; naming the field and problem enables precise self-correction. Other categories trigger wrong behaviour; empty success hides the failure.

### a2-err-05
skill: 2.2
scenario: S3
Where should transient errors from a web-search API preferably be handled in a multi-agent research system?
- [ ] Only in the coordinator, which retries the whole subagent task whenever any search call fails
- [x] Locally in the search subagent or tool, with retries, before propagating anything it cannot resolve
- [ ] Nowhere — transient errors should be ignored because they usually resolve themselves over time

### a2-dist-01

scenario: S3
A synthesis agent was given all 18 tools in the research system "for flexibility". It now runs its own web searches instead of synthesising, and tool-selection errors have increased. What is the best change?

- [ ] Keep all tools but add a system-prompt rule telling the synthesis agent never to search the web itself
- [ ] Give all agents all tools so that each of them can independently complete any part of the work
